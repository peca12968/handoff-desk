# Crew Cover｜活動人員排班與缺席試算

活動同時需要報到、音控、直播和字幕人員。把通才 Mei 派到她最喜歡的早班報到，就會錯過只有她能支援的試音。Crew Cover 一次考慮整場活動的需求，列出每班的人選、空缺與整份班表的偏好成本。現場有人請假時，可以保留原始需求，用同一份輸入重算。

## 重現一位成員缺席的結果

在 Python 3.12 環境中執行以下指令。資料與人名皆為合成。

```sh
python -m pip install -r requirements.txt
python crew_cover.py examples/conference.json
python crew_cover.py examples/conference.json --absent bao
python -m unittest -v
```

| 班別與活動開始後的分鐘數 | 四人全到 | Bao 缺席 |
| --- | --- | --- |
| 報到，0–120，需 2 人 | Lin、Yu | Lin、Yu |
| 試音，60–180，需 1 人 | Mei | Mei |
| 服務台，120–240，需 1 人 | Lin | Lin |
| 直播，180–300，需 1 人 | Bao | Mei |
| 字幕，180–240，需 1 人 | Mei | 缺 1 人 |
| **已補人次／需求人次** | **6／6** | **5／6** |
| **偏好成本** | **9 點** | **5 點** |

Bao 缺席時，直播與字幕在第 180 分鐘同時開班，只剩 Mei 有資格支援這兩項工作。即使 Yu 願意接字幕，他仍缺少字幕技能。最多只能補到五人次。在同樣能補五人次的方案中，Mei 接直播的總成本最低。兩張班表涵蓋的人次不同，偏好成本適合用於比較相同覆蓋率的方案。[範例輸入](examples/conference.json)

## 班表已公布後，有人請假

把上次輸出的 JSON 存為已公布班表，重排時用 `--baseline` 讀回。工具先補足最多人次，再找出班次組合有變動的最少人數，最後在這兩項條件下選出偏好成本最低的安排。

```sh
python crew_cover.py examples/conference.json > published.json
python crew_cover.py examples/conference.json --absent bao --baseline published.json
```

| Bao 缺席後的排法 | 補足名額 | 與已公布班表相比 | 待補名額 | 偏好成本 |
| --- | --- | --- | --- | --- |
| 依偏好重排 | 5／6 | Bao 退出直播，Mei 從字幕換到直播，共 2 人有異動 | 字幕 1 人 | 5 點 |
| 依已公布班表重排 | 5／6 | 僅 Bao 退出直播，其他 3 人照原班表出勤 | 直播 1 人 | 6 點 |

`changes.by_person` 逐人列出移除與新增的班別。`changes.people` 包含缺席者，同一人即使換了好幾班也只計一次。兩次排班用人員與班別識別碼比對。若上次的班別或成員已刪除，原指派會列入移除清單。若班別改期且希望讓異動清單反映這次改期，請給新時段新的班別識別碼。重排結果也能用作下次的已公布班表。

## 活動進行到一半才請假

Lin 已經完成第 0 到 120 分鐘的報到班，但無法接第 120 分鐘開始的服務台。把交接時間與已公布班表一起傳入，就能保留報到紀錄，也保留第 60 分鐘已開始的試音班。

```sh
python crew_cover.py examples/conference.json > published.json
python crew_cover.py examples/conference.json --baseline published.json --absent lin --handover-at 120
```

| 缺席生效時間 | Lin 的報到班 | Lin 的服務台班 | 整場已補名額 |
| --- | --- | --- | ---: |
| 全天缺席 | 移除 | 移除 | 4／6 |
| 第 120 分鐘交接 | 保留 | 移除，空缺 1 人 | 5／6 |

`handover.locked_shifts` 列出開始時間**早於**交接點的班次，包含已結束及仍在進行的班。既有人選與空缺都會保留，整班分鐘數照計入成員工時。剛好在交接點開始的班可重新分配。本案例中 Yu 已用完 120 分鐘配額，Mei 仍在試音，兩人都無法補服務台。若 Lin 已開始服務台且能完成當班，將交接點改為第 121 分鐘，服務台就會保留。此模型以完整班次為單位，中途換手需要事先把工作拆成兩班。

新輸出以 `shift_windows` 記錄公布時段，可偵測有人移除或改期已開始的班。若新資料把已出勤者的預算降到低於既有工時，程式會回報衝突。較早版本的輸出也可作為基準，會用現有識別碼與時段判定已開班範圍。如果舊輸出沒有時間資訊，且某班識別碼已被移除，工具會回報無法判定開班時間。可依照原先的活動時程重新產生基準。

測試另外產生 100 組活動進行中的班表，以獨立窮舉保留已開班人選，檢查可行性、最大覆蓋、最少異動人數及偏好成本。[驗證程式](test_crew.py)

## 用自己的需求排班

輸入 JSON 的 `shifts` 與 `crew` 各以唯一識別碼為鍵。

| 欄位 | 意義 |
| --- | --- |
| start、end | 從活動起點算起的整數分鐘。一班的結束可接下一班的開始。 |
| need、skill | 全班所需人數與必要技能。每人須能支援完整班次。 |
| skills、budget_minutes | 成員具備的技能，以及本次活動可被安排的總分鐘數。 |
| bids | 成員可出勤的班別及各自的非負整數成本。0 表示最偏好，省略表示無法出勤。 |

每班可安排多人，每人可接多班。工具會檢查技能、可出勤班別、時間重疊與總工時。`--absent` 可重複傳入多位成員。輸出 JSON 以 `assigned` 列出人選，以 `vacant` 標示仍待補足的人數。同樣覆蓋與成本可能對應多張班表，輸出其中一張。

## 求解與驗證

每一個符合技能與可出勤條件的配對對應一個布林變數。CP-SAT 會固定前一階段已證明的最優值，再處理下一個目標。帶入已公布班表時，同一人的所有指派差異合併成一個異動指標。每個階段都取得最優狀態後才輸出結果。[排班實作](crew_cover.py) · [OR-Tools 排班文件](https://developers.google.com/optimization/scheduling/employee_scheduling) · [求解狀態定義](https://developers.google.com/optimization/cp/cp_solver)

測試產生 100 組可重現的小型班表，獨立列舉每班可選的人員組合，再逐分鐘檢查每人是否重複出勤。每一組都核對輸出班表的可行性、最大覆蓋人次與最低成本。另把單班成本調高至 20 億點，驗證仍會優先滿足六個名額。窮舉只用於小型案例的交叉驗證。[獨立驗證](test_crew.py)

另有 100 組重排案例先產生已公布班表，指定一人缺席，更新工時與偏好。測試逐一窮舉新版班表，核對最大覆蓋人次、最少異動人數和最低成本，並從新舊指派獨立還原每人的異動清單。

本專案使用 AI 輔助開發，展示限制式建模、最佳化與結果驗證。
